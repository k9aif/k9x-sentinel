Every finding ever sent for human review, from Sentinel's append-only audit trail. A case waiting longer than the overdue limit is a governance gap: ask the reviewers why it hasn't been decided.

How a finding moves

  1. Collect. Every morning at 06:00 Sentinel reads the threat-intelligence feeds and asks OSV about every dependency k9-aif declares. Only new items are kept; items older than 14 days when a source is first seen are recorded as baseline and never assessed.
  2. Screen. Each article is checked by k9x Shield and Granite Guardian. Attack write-ups usually contain live injection examples, so the result is a label on the finding, not a block: hiding the article would hide the threat.
  3. Compare. The model reads the article next to the framework's capability catalog (capabilities.yaml, shipped in k9-aif) and answers covered, partial, gap or not relevant, with the OWASP ids, matching controls, severity, confidence, rationale and a suggested fix. It has no tools, and any id not in the catalog is discarded. Dependency findings skip this step: they are decided by version arithmetic alone.
  4. Triage. Only relevant gaps or partial gaps of at least medium severity and 0.5 confidence go further. An instance of a gap the maintainers already know about is recorded against it unless it is high severity or worse.
  5. Raise. Each finding is its own flow. The triage agent raises RequiresHIL; the orchestrator hands it to the framework's BaseHILOrchestrator, which publishes the case to k9x-hil.
  6. Review. A reviewer approves or rejects it in k9x-hil (or it expires after 14 days). The case carries only the finding number, verdict, severity and a link back here.
  7. Act. The framework's router receives the decision and resumes the same flow exactly once. From an approved reviewer, an approval becomes a private draft security advisory (technique gaps) or an issue (dependency floors) on k9-aif-framework; everything else is recorded. Sentinel never changes code.
